# 開発方針

## 目的

このリポジトリでは、自然言語の仕様書を唯一の正本とせず、変更の意図を起点として、契約と検証に基づいて開発を進める。

自然言語は、解決したい問題、利用者の意図、判断理由を伝えるのに適している。一方で、表現に幅があり、コードとの意味的一致を機械的に保証できない。また、実装前には分からなかった制約が実装中や運用中に判明するため、事前設計が常に正しいという前提も置かない。

そこで、情報の性質に応じて、自然言語、Schema、制約、テスト、コード、実行結果、運用観測を使い分ける。設計と実装を一度で確定するのではなく、小さな変更と検証から得た事実を次の判断へ反映する。

## この方針の位置付け

「契約と検証に基づく開発」は、業界で確立された単一の開発手法の名称ではない。このリポジトリでは、次の既存の実践を必要に応じて組み合わせる。

- Executable Specification / ATDD: 重要な振る舞いを受け入れテストで表す
- Contract-First Development: 外部との境界をSchemaや明示的な契約で表す
- Docs as Code: 長期的に必要な文書をコードと同じようにレビューする
- Delta Specification: 現在仕様全体を複製せず、今回の変更点を記録する
- ADR: 長期的に重要な設計判断と理由を残す
- Architecture Tests / Fitness Functions: 構造や非機能上の重要な性質を継続的に検証する
- Evaluation-Driven Development: 実装、評価、修正のループで完成度を上げる

これらをすべての変更で要求するものではない。変更のリスクと、守る必要がある性質に応じて必要なものだけを使う。

## 用語

### 意図

今回の変更によって、誰のどのような問題を解決し、何を変えたいのかを表す。実装手段ではなく、変更する理由と期待する結果を中心に記述する。

### 契約

システムの境界で、呼び出し側、利用者、保存済みデータ、外部プロセスなどに対して守ると決めた内容を指す。例えば次を含む。

- CLI、API、Native Messagingの入出力
- メッセージ、設定、ファイルなどのSchemaと形式
- 永続データの制約と互換性
- セキュリティ境界と許可する操作
- 外部から観測できる重要な振る舞い

内部関数、クラス構成、一時的な中間データまで無条件に契約として固定しない。内部実装は、外部契約と必要な不変条件を守る範囲で変更できる。

### 検証

意図した結果、契約、重要な性質が満たされているかを確かめる行為と証拠を指す。例えば次を含む。

- 単体テスト、受け入れテスト、契約テスト、統合テスト
- Schema検証、DB制約、型検査、静的解析
- アーキテクチャテスト、依存関係や循環参照の検査
- 負荷試験、障害試験、セキュリティ検査
- 実行結果の確認、ログ、メトリクス、アラート
- 自動化できない価値判断に対する人間のレビュー

テスト結果だけを唯一の合否判定にはしない。自動化できない体験や価値判断は、人間が確認する。

## 開発原則

### 設計は正解ではなく仮説として扱う

実装前の設計と計画は、その時点で得られている情報に基づく仮説である。

```text
意図
  ↓
設計仮説
  ↓
実装と検証で事実を得る
  ↓
設計、契約、検証方法、または実装を見直す
```

実装が当初設計と異なること自体を失敗とは扱わない。意図と合意した契約を満たすかを確認し、変更した判断や新しく判明した制約を残す必要があるかを判断する。価値のなくなった事前設計を、現在仕様に見せかけて維持し続けない。

### コードを正解とはみなさない

コードと実行結果は、現在システムが実際に行うことを知るための強い証拠である。しかし、バグや暫定実装を含む可能性があるため、何を行うべきかの正解とは限らない。

現在動いている挙動は、明示的に変更すると決めるまでは後方互換性の初期値として扱う。変更する場合は、変える挙動と維持する挙動を明らかにし、必要な契約と検証を更新する。

### 問いごとに証拠を使い分ける

単一の文書、テスト、Schema、コードを万能な正本にしない。

| 問い | 主な証拠 |
| --- | --- |
| なぜ変更するのか | vision、Issue、変更の意図 |
| 何を保証するのか | 受け入れ条件、Schema、契約、不変条件 |
| 実際に何が動くのか | コード、実行結果、実行環境 |
| 保証を満たすか | テスト、評価、監視結果 |
| なぜ設計を選んだのか | ADRまたは意思決定の正本 |
| 現在どのような構造か | コード、Schema、コードから生成・検証した資料 |

### 機械的な保証を優先する

重要な制約は、可能な限り実行可能な形へ落とす。自動化できる制約を注意書きだけで済ませず、Schema、型、データ制約、テスト、静的解析、監視など、制約に適した仕組みで検証する。

一つの検証方法だけで十分とは限らない。例えば、任意コマンドの実行を防ぐという意図は、入力検証、シェルを介さないプロセス起動、許可する操作の制限、異常系テストなど複数の層で守る。

### 自然言語には理由と境界を残す

自然言語で長期管理するのは、主に次の内容とする。

- 解決したい問題と利用者の意図
- 外部から観測できる重要な振る舞い
- 守るべき不変条件と境界
- 設計判断の理由とトレードオフ
- コードから復元できない背景

次の内容は、原則として自然言語に重複して保持しない。

- 関数、クラス、内部処理の逐次説明
- Schemaから生成できるフィールド一覧
- CLIやmanifestから生成できる定義一覧
- import解析から生成できる依存関係
- migrationから生成できる現在のデータ構造

### 変更の儀式はリスクに比例させる

小さく可逆的な変更に、詳細な設計書やADRを要求しない。一方、外部互換性、データ損失、セキュリティ、復旧性などに影響する変更では、必要な契約、移行方法、異常系、運用上の検証を事前に明らかにする。

## 情報の置き場所

同じ情報を複数の場所へ複写しない。ある場所をその情報の正本とし、他の場所からはリンクまたは短い参照だけを置く。

| 情報 | 主な置き場所 | 更新する契機 |
| --- | --- | --- |
| プロダクトの目的と長期的な範囲 | README、vision文書 | 目的や対象範囲を変更したとき |
| アイデア、優先順位、探索中の議論 | Issueや利用中の課題管理場所 | 検討や優先順位が変わったとき |
| 一つの変更の意図と受け入れ条件 | Issue、変更提案、PRのいずれか一つ | 変更内容について合意が変わったとき |
| 外部契約と永続形式 | Schema、型定義、migration、契約テスト | 境界や互換性を変更したとき |
| 現在の実装と構造 | コード、設定、生成資料 | 実装を変更したとき |
| 長期的に重要な設計判断 | ADRまたは共有する意思決定場所 | 判断を採用、却下、置換したとき |
| 検証結果 | CI、テスト結果、評価結果、監視 | 対象の変更または実行時 |

Issue、PR、ADRなどの具体的な利用先が決まっていない場合でも、情報の正本を一つにする原則は維持する。リポジトリ外に正本を置く判断も許容するが、コードを変更する際に必要な判断は、実装から辿れるように参照を残す。

## 証拠が食い違った場合

自然言語、契約、テスト、コード、実行結果に対する絶対的な優先順位は設けない。食い違いを見つけた場合は、機械的にどれかを正しいものとして書き換えず、まず次を明らかにする。

1. どの問いに対する証拠が食い違っているか
2. 既存バグ、古い契約、誤ったテスト、新しい要求、環境差のどれに当たるか
3. 現在の挙動を維持、変更、または移行する必要があるか
4. 判断によって影響を受ける契約、検証、実装、文書は何か

最終的な判断は、人間が意図、互換性、リスク、得られた事実を確認して行う。エージェントは矛盾と選択肢を報告し、判断を暗黙に代行しない。

## 変更フロー

### すべての変更で行うこと

1. 変更の意図を一文で説明する。
2. 現在の挙動と関連する証拠を確認し、変えるものと維持するものを区別する。
3. 影響を受ける契約と、必要な検証方法を決める。
4. 一つの意図を保てる小さな単位で実装する。
5. リスクに応じた検証を行い、結果を確認する。
6. 実装中に判明した事実を反映し、古くなった契約、テスト、文書を更新または削除する。

外部動作を変えないリファクタリングでは、意図と既存の保証を確認できれば、製品仕様やADRの更新を要求しない。

### 追加検討が必要な変更

次のいずれかに当てはまる場合は、高リスクな変更として追加の検討と検証を行う。

- 外部インターフェースまたは永続データの互換性を変える
- データ損失、破損、上書き、取り消せない操作につながる
- 認証情報、署名付きURL、ファイルパス、プロセス起動などのセキュリティ境界に触れる
- WebExtension、Native Host、ffmpegなど、プロセスや権限の境界を越える
- 並行処理、再試行、重複排除、タイムアウト、キャンセルに影響する
- 性能、可用性、復旧性、リソース使用量に大きく影響する
- 新しい外部依存または運用上の前提を追加する

必要に応じて、次を追加する。

- Schemaと契約テスト
- 互換性と移行方法
- 異常系、境界値、セキュリティのテスト
- 測定可能な非機能要件と評価方法
- ロールバックまたは安全な段階導入の方法
- ログ、メトリクス、アラートなどの運用確認
- 長期的な判断を残すADR

## 完了条件

変更は、少なくとも次を満たしたときに完了とする。

- 変更の意図を説明できる
- 意図した動作と、維持すべき既存動作を確認できる
- 影響を受ける契約が実装と一致している
- リスクに見合った検証が成功している
- 新しく判明した重要な制約または判断が、適切な場所に反映されている
- 古くなったテスト、契約、文書が現在仕様に見せかけて残っていない

未解決のリスクを受け入れて完了とする場合は、その内容と理由を追跡可能な場所に残す。

## 文書の維持と分割

この文書には、個別機能の仕様、実装の逐次説明、変更ごとの受け入れ条件を複写しない。この方針自体を変更した場合にだけ更新する。

内容が増え、異なる頻度で更新される部分が明確になった場合に、`docs/development/` 以下へ分割する。ファイル数を先に決めず、実際の変更理由と参照方法が異なる単位で分ける。

ADRは長期的に重要な判断が初めて発生した時点で `docs/decisions/` または適切な共有場所に作成する。空のディレクトリや雛形は事前に作らない。
