# 変更ルール

## 参照タイミング

- 変更へ着手する前に参照する。
- 変更を完了と判断する前に再度参照する。

## すべての変更で行うこと

1. 変更する理由または確かめたいことを説明できるようにする。差分から自明な変更では、独立した記録を要求しない。
2. 現在の挙動と関連する証拠を確認し、変えるものと維持するものを区別する。
3. 影響を受ける契約と、必要な検証方法を決める。
4. 一つの目的を保てる小さな単位で実装する。
5. リスクに応じた検証を行い、結果を確認する。
6. [`information-lifecycle.md`](information-lifecycle.md) に従って、実装中に判明した事実を反映する。

外部動作を変えないリファクタリングでは、変更目的と既存の保証を確認できれば、製品仕様やADRの更新を要求しない。

## 追加検討が必要な変更

次のいずれかに当てはまる場合は、高リスクな変更として追加の検討と検証を行う。

- 外部インターフェースまたは永続データの互換性を変える
- データ損失、破損、上書き、取り消せない操作につながる
- 認証情報、署名付きURL、ファイルパス、プロセス起動などのセキュリティ境界に触れる
- WebExtension、Native Host、ffmpegなど、プロセスや権限の境界を越える
- 並行処理、再試行、重複排除、タイムアウト、キャンセルに影響する
- 性能、可用性、復旧性、リソース使用量に大きく影響する
- 新しい外部依存または運用上の前提を追加する

必要に応じて、次を追加する。

- Schemaと契約テスト
- 互換性と移行方法
- 異常系、境界値、セキュリティのテスト
- 測定可能な非機能要件と評価方法
- ロールバックまたは安全な段階導入の方法
- ログ、メトリクス、アラートなどの運用確認
- 長期的な判断を残すADR

## 完了条件

変更は、少なくとも次を満たしたときに完了とする。

- 変更する理由または確かめたことを説明できる
- 目的とした動作と、維持すべき既存動作を確認できる
- 影響を受ける契約が実装と一致している
- リスクに見合った検証が成功している
- 新しく判明した重要な制約または判断が、適切な場所に反映されている
- 古くなったテスト、契約、文書が現在仕様に見せかけて残っていない

未解決のリスクを受け入れて完了とする場合は、その内容と理由を追跡可能な場所に残す。
